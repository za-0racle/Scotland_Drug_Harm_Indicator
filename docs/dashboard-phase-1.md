# Analytical dashboard Phase 1

Implemented locally on 9 November 2026. No production data, schema, RLS policy or grants were changed; no migration was executed and nothing was deployed. The existing public read access is used as supplied. The historical migration remains untouched.

## Architecture and data flow

- `src/supabase.js`: reusable publishable-key client; no persisted auth session or privileged browser key.
- `src/database.js`: explicit-column reads of mortality_quarterly, indicator_configurations and indicator_results only; chronological ordering, foreign-key configuration label embedding, pagination and distinct error/empty states. Incomplete paginated responses fail rather than claiming a full load.
- `src/main.js`: refresh orchestration, concurrent dataset reads and setup errors. Refresh clears old data so failed reads cannot leave stale numbers presented as refreshed.
- `src/analytics.js`: immutable chronological sorting, inclusive year filtering, configuration-ID matching, stored-flag selection, summary counts and gap-aware series transformations.
- `src/charts.js`: Chart.js rendering, exact raw-value tooltips, straight line segments and null gaps. Old chart instances are destroyed before filter/refresh replacement, following the [Chart.js lifecycle API](https://www.chartjs.org/docs/latest/developers/api.html).
- `src/dashboard.js`: accessible controls, dynamic summary cards, responsive charts, exact-value expandable tables, methodology and retained database verification details. Database text uses textContent rather than HTML insertion.
- `src/style.css`: navy, teal and white theme with mobile layouts and scrollable tables.

All observations/configurations/results are loaded from Supabase on page load and manual refresh. Controls filter those live response arrays locally, without additional calls or inferred values. Summary cards cover all retrieved data and remain unfiltered. An unavailable dataset is shown as unavailable, not zero; zero recorded flags is shown only when actual result rows have been retrieved with no true flags. No mock datasets are included in runtime code.

## Statistical interpretation

The mortality source was verified through a read-only CLI join to data_sources: Police Scotland suspected drug deaths, Jan 2017–Dec 2025, Scottish Government Oct–Dec 2025 release. The source publication link is curated page content; the public browser never requests data_sources or other unapproved tables.

The four available configurations come from the database and are selected using their actual configuration IDs. The initial selection prefers a configuration with a recorded signal, when present, so the retrospective finding is visible. Labels, IDs, parameters, descriptions, verification notes and computation references are retained. Current coverage is 36 mortality quarters (2017 Q1–2025 Q4), four models and 76 outputs. Those values are assertions in live browser checks, not constants driving dashboard cards.

NB2-EWMA displays stored per-quarter statistics and limits. One stored flag is present for the 16-quarter model in 2022 Q3: statistic -1.16480084, lower limit -0.9873333333, upper limit 0.9873333333. This is a retrospective model flag, not a clinical alert or validated public health warning. Flags are not generated by comparing numbers in the browser.

For the two-sided opioid-share CUSUM, the reviewed computation references specify calibration at 2022 Q1–2023 Q4, reset at 2024 Q1, and monitoring in 2024. Four monitoring outputs are available. Positive and negative components are plotted separately with the stored upper decision limit. The stored zero lower_limit is shown in the table as a reset baseline, never as a lower alarm line. K=0.5 SD and H=4.77 SD are configuration parameters; they are not substituted for the stored-scale decision limit. No unavailable calibration observations are fabricated or plotted.

Exact JavaScript numeric values are retained in table text and tooltips; plotted axes use readable ticks. Null quarterly slots create gaps only, never observations, counts or interpolated values. The model result tables contain every selected result, including the stored statistic for CUSUM and both components. Mortality filtering does not change model coverage or summary counts.

## Verification

Commands from the repository root:

```powershell
npm test
npm run build
npm run test:e2e
npm run dev
```

Unit tests cover chronological ordering, inclusive and inverted year ranges, missing quarters, zero values, configuration matching, raw numeric preservation, recorded flag selection, CUSUM series semantics, summary availability, explicit-column scope, pagination, missing configuration, RLS-style empty responses and database/network errors.

Playwright uses the installed Edge channel on Windows and Chromium elsewhere. For other platforms, install the browser with `npx playwright install chromium`. Live checks require configured environment variables and the current approved research dataset. They read only the three approved tables, verify all four model selections, refresh, invalid ranges, exact CUSUM values and 390px layout overflow. A network-failure test aborts requests without supplying fabricated records. Screenshots show actual live Supabase data. No test changes remote data or permissions.

## Remaining limitations

This is a retrospective research interface, not validated operational monitoring. No new model fitting, calibration, uncertainty estimates, rates, population adjustment, prospective validation, alert ingestion or RADAR intelligence integration is implemented. Only the three approved tables are queried. Model coverage differs by configuration; CUSUM has only four monitoring observations. Some stored configuration notes still state outputs require verification; they are displayed unchanged. Browser tables/tooltips reflect JavaScript numeric precision, not arbitrary-precision PostgreSQL decimals. Future source/coverage or model-method changes require reviewing the curated provenance and CUSUM period notes. A source API/backend is not introduced.
